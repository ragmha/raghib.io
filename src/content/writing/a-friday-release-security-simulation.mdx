It is Friday afternoon. A small software team is preparing a release that lets
customers search their invoices. The pull request is almost ready. The feature
works with the test account, and the release is already on the calendar.

Then a security check raises an alert.

This is a fictional scenario, not a report of a real incident. I want to use it
to explore a more practical question than "which scanners can I turn on?":

**Can a team turn a security finding into a safe release decision without
treating a green check as proof that the feature is secure?**

## The feature

Imagine a multi-tenant billing service. Each customer should be able to search
only its own invoices. The new endpoint accepts an invoice number and looks up
the matching record.

In the rushed version, the code builds a database query by joining the invoice
number into a SQL string. That creates an injection risk. Depending on the
query, database permissions, and the data it can reach, an attacker could
change what the query returns. A separate authorization check must still make
sure the caller is allowed to see each returned invoice.

In simplified C#, the difference looks like this. It is illustrative, not code
from the demo repository:

```csharp
// Rushed: the invoice number becomes part of the SQL text.
var sql = $"SELECT * FROM Invoices WHERE Number = '{invoiceNumber}'";

// Safer: input stays a parameter, and every read is scoped to the tenant.
// The tenant ID comes from the signed-in caller, never from the request.
const string sql =
    "SELECT * FROM Invoices WHERE Number = @number AND TenantId = @tenantId";
command.Parameters.Add("@number", SqlDbType.NVarChar, 32).Value = invoiceNumber;
command.Parameters.Add("@tenantId", SqlDbType.UniqueIdentifier).Value = caller.TenantId;
```

Those are related concerns, but they are not the same fix. [Using query
parameters][owasp-sqli] addresses the injection path. [Enforcing tenant
access][owasp-authz] addresses who may read a record. One should not be treated
as a substitute for the other.

## What I would simulate

The public demo repository already contains an ASP.NET application, intentionally
vulnerable samples, and security workflows. I would use a separate fork and
synthetic invoice data, then create a small pull request that adds the search
feature with the unsafe query.

The experiment would follow the change through a normal review:

1. Run the application's build and tests.
2. Let the pull-request security checks run and record the exact alerts they
   produce.
3. Review whether each alert is relevant to this change and whether anything
   important is missing.
4. Replace the unsafe query with a parameterized one, enforce tenant
   authorization, and add tests for a valid search, an unauthorized tenant,
   and input that looks like SQL.
5. Rerun the checks and make the release decision based on the code, tests, and
   alert results together.

I would not assume the scanner finds this particular issue. That is one of the
things the simulation is meant to test. If it does not, that is useful evidence
about the limits of this setup—not a reason to quietly change the example until
it produces the result I expected.

## The decision is part of the demo

An alert does not make the release decision by itself. Someone has to determine
whether the finding is real, what data and permissions are in scope, and
whether the proposed fix closes the path without breaking the feature.

The team should hold the release while it investigates a credible path to
unauthorized data access. If the alert is a false positive, the reviewer should
be able to explain why. If the fix changes query behavior, the tests should
exercise that behavior—not just assert that a particular API appears in the
source.

An AI-generated suggestion could help draft a fix. It would still need review
and verification. A patch that silences a finding but drops the tenant check,
or breaks valid invoice searches, is not a successful remediation.

That distinction is easy to lose in a demo. A green check answers a narrower
question: the configured check passed. It does not establish that every
security property of the feature has been tested.

## What I would measure

I would keep the evidence small and observable:

- Did the configured checks identify the seeded issue?
- Did they report anything unrelated?
- Did the regression tests distinguish authorized from unauthorized access?
- Did the corrected change pass the same checks?
- What did a human reviewer need to verify before approving it?

I would publish the actual run output, including a miss or false positive. I
would not invent a time saved, a reduction in risk, or a production impact.
This simulation can show how one team might handle one change; it cannot
establish how often a tool finds vulnerabilities across real organizations.

## Keep the boundary visible

The setup should stay isolated: a fork, synthetic records, and no production
credentials or services. The point is to reproduce a believable development
decision, not to create a real customer-data path or claim a breach occurred.

The lesson I want to test is modest. Security tools can make a risky change
visible in the same workflow where it is being built. The team still has to
understand the boundary being protected, verify the fix, and decide whether
the evidence is enough to ship.

For this feature, that boundary is straightforward to state: a customer may
search its invoices, but it must not be able to read another tenant's data.
The useful question is whether the code, tests, and review process make that
rule true—not whether the dashboard is green.
