## Start with where the component runs

React Server Components (RSC) render on the server. Their component
implementation is not sent to the browser as client JavaScript; React sends
the rendered result in its server-component payload instead. That can reduce
the JavaScript a page needs, but it does not mean the whole page has no
JavaScript.

```tsx
// This component runs on the server only
// No JavaScript is sent to the client for this code
async function RecentPosts() {
  const posts = await db.query('SELECT * FROM posts ORDER BY date DESC LIMIT 5')

  return (
    <ul>
      {posts.map(post => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

## Server and client components have different jobs

In a framework that supports RSC, the distinction is about where component
code can run and what it can do:

### Server Components (default)
- Run on the server during rendering
- Can access server-side data sources such as databases and files
- Cannot use hooks (`useState`, `useEffect`)
- Cannot add event handlers (`onClick`, `onChange`)
- Their implementation is not included in the client JavaScript bundle

### Client Components (`'use client'`)
- Can be server-rendered, then hydrated in the browser
- Can use hooks and interactivity
- Their client-side code is included in the JavaScript bundle
- Declared with the `'use client'` directive at the top of the file

```tsx
'use client'

import { useState } from 'react'

export function LikeButton() {
  const [likes, setLikes] = useState(0)
  return (
    <button onClick={() => setLikes(l => l + 1)}>
      ♥ {likes}
    </button>
  )
}
```

## Compose the two

Server components can render client components, passing data to the interactive
part of the page. Client components cannot import server components. Keep
database access and other server-only work on the server; put state and event
handlers in the client component that needs them.

```tsx
// Server Component — fetches data
async function PostPage({ id }: { id: string }) {
  const post = await getPost(id)

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
      {/* Client component for interactivity */}
      <LikeButton postId={id} />
      <CommentSection postId={id} />
    </article>
  )
}
```

## Choose the boundary

Start with server components for data and rendering. Add a client component
where the interface needs browser interaction:

- **Need database access?** → Server Component
- **Need user interactivity?** → Client Component
- **Rendering a list of items?** → Server Component
- **Managing form state?** → Client Component
- **Displaying static content?** → Server Component

Do not add `'use client'` just in case. It moves that component and its
dependencies into the client bundle, so use it where interaction requires it.

## What changes for performance

RSC can reduce client JavaScript when server-only components and dependencies
stay on the server. The result depends on the component boundary and the
framework; RSC does not automatically make every page faster.

It can also let a server component read data without adding a separate browser
request to an API route, and supported frameworks can stream rendered output
as it becomes ready. Those are options to measure in an application, not
guaranteed performance wins.

This site now uses Astro, but the same architectural question still matters in
React applications: ship client JavaScript only where interaction requires it.
