Every vendor review seems to begin the same way: someone sends a spreadsheet, someone else searches old answers, and both sides spend time reconciling versions.

The spreadsheet is not the problem by itself. It is a portable protocol: it defines the questions, the expected answers, and the record both parties can keep. The trouble is that the protocol travels as a file. Answers get copied forward, evidence goes stale, and the buyer cannot easily tell whether a response is a current fact, a policy statement, or a guess.

What if the buyer's system could ask the vendor's system directly—and receive not just an answer, but the evidence and limits behind it?

## The answer is not another chatbot

A vendor chatbot can make it easier to search a trust center. That is useful, but it does not automatically solve the harder problem: can a buyer rely on the answer, trace it to evidence, and record what was actually checked?

The experiment I want to test is narrower. A vendor publishes a small, authenticated interface for approved responses. A buyer's agent asks a specific question. The vendor side returns an answer, its source, when it was reviewed, and—where the claim can be checked—an evidence result. The buyer's system stores that response in a review record.

The result is not an autonomous approval. It is a better first draft of the review, with uncertainty visible instead of buried in a spreadsheet cell.

## Give each tool one job

Several pieces of the agent ecosystem could fit, but they solve different parts of the problem:

- **MCP** can expose narrow tools to an agent, such as retrieving an approved answer or checking a named control.
- **A2A** could support communication between a buyer-side agent and a vendor-side agent. It is a possible exchange mechanism, not a guarantee that the parties agree on the meaning or authority of an answer.
- **An agent gateway** could enforce identity, authorization, rate limits, and logging at the vendor's boundary.
- **Kusto** could query time-stamped operational evidence, such as synthetic control observations, to check whether a statement is supported.
- **A buyer-side agent**, perhaps something like Goose, could assemble questions and responses into a review the buyer can inspect.

These are candidate components, not a finished architecture. MCP does not define the commercial relationship between buyer and vendor. A2A does not make the answer true. A gateway cannot make an outdated policy current. The governance still has to come from the people and systems responsible for the claim.

## Make uncertainty a first-class result

Consider a buyer asking whether privileged accounts require multifactor authentication.

The vendor's approved answer says yes. A read-only query against synthetic Kusto observations checks the latest available control data and finds one account without MFA. A useful response should not collapse those two pieces of information into a confident “yes.”

It should say that the written statement requires MFA, the latest observation found an exception, and the evidence therefore does not fully support the statement. It should include the observation time and scope, then route the discrepancy to a person.

The tool should also return **unknown** when evidence is missing and **stale** when evidence has passed its review window. “No evidence” is not the same as “no issue”; a control policy is not the same as proof that the control is working.

That distinction is the point of using a query system like Kusto in the experiment. It gives the demo a way to contrast a vendor's approved statement with a separate, time-stamped observation. The data would be synthetic: the goal is to test the shape of the exchange, not imply access to any real company's controls.

## Start with one question, not an ecosystem

The first version needs only two read-only operations:

1. Retrieve one approved answer with its owner, source, and last-reviewed date.
2. Check one named control and return a bounded evidence summary.

Keep the Kusto query fixed and parameterized. Do not let the model submit arbitrary KQL, and do not return raw account records when an aggregate result is enough. Require buyer authorization, log what was requested, and make it clear when a human must review the result.

Then test three cases: evidence supports the answer, evidence contradicts it, and the system cannot determine either way. Add a stale-evidence case if those first three work. Only after that would I connect a buyer agent over A2A or put an agent gateway in front of the vendor service.

This keeps the experiment small enough to learn from. It also makes failure legible: if a claim cannot be tied to evidence, the system says so instead of producing a polished paragraph that sounds complete.

## The hard part is trust, not transport

It is tempting to think the missing piece is a protocol. But a protocol only moves a request and response. Buyers still need to know who approved the answer, which evidence supports it, how recent that evidence is, and what to do when the statement and observation disagree.

There are adoption questions too. Vendors may not want to expose internal systems. Buyers may require a particular spreadsheet or portal. Legal and procurement teams may treat a machine-generated response differently from a signed attestation. The experiment should preserve a human approval step and keep an export path, rather than pretending those constraints disappear.

The useful shift is not “replace every spreadsheet with an agent.” It is to separate the questions from the file that happens to carry them. If questions become structured requests and answers arrive with traceable evidence, a spreadsheet can remain an export format—not the source of truth.

That is what I want to test: not whether agents can fill in a questionnaire, but whether two organizations can exchange a review that is easier to verify than the document they started with.
