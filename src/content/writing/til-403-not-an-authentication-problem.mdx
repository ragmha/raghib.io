**Disclaimer:** I work at Microsoft. This is my personal view, based only on public information. It isn’t an official position or a product recommendation.

*How I investigated two failing GitHub Agentic Workflows—and why the fix wasn't to
raise their AI-credit limits.*

One workflow spent **10.37 credits against a cap of 5**. Another spent **10.70
against a cap of 8**. Both runs made one model request. The error said:

```text
Authentication failed with provider (HTTP 403).
```

My first reaction was to suspect credentials or permissions. I initially raised
the workflows' AI-credit caps, then checked the run data before treating that as
the fix. The audit pointed somewhere else.

## The audit changed the diagnosis

I audited the failed runs with `gh aw audit` and compared the model usage with
each workflow's configured cap.

| Workflow | Model used | Cache writes | Credits consumed | Cap |
| --- | --- | --- | --- | --- |
| Meeting-insight capture | Claude Sonnet 5.5 | 37,082 tokens | 10.37 | 5 |
| Account status notes | Claude Sonnet 5.5 | 38,393 tokens | 10.70 | 8 |

Each run made **one model request** and read **zero cached tokens**. That first
request wrote about 37,000 tokens to the prompt cache—and cost more than the
workflow's entire budget.

## What the 403 was actually reporting

The first request loaded the workflow's context and used up its credit budget.
When the workflow tried to continue, the proxy rejected the next request. That
budget failure surfaced as HTTP 403, which made a cost problem look like an
authentication problem.

The cache numbers were another clue. A cache write does not mean the workflow is
benefiting from caching. These runs had no cache reads.

Caching can make stable context cheaper on later requests—but only if those
requests happen and the cache can be reused. The workflows hit their caps before
reaching that point. Optimizing for multi-turn cache reuse would not have fixed a
first-request failure.

## The fix: make the first request cheaper

Raising the caps would have let the same expensive startup context consume more
credits without addressing why it cost so much. I kept the original caps instead:
5 credits for meeting-insight capture and 8 for account status notes. For what
should happen when a budget cap does trip, see
[Keep Shipping: When an AI Budget Runs Out](/writing/keep-shipping-copilot-budget-limits-part-1/).

The configured model was `auto`, which routed these runs to Claude Sonnet 5.5. I
pinned the workflows to **GPT-5.6 Luna**, a lower-cost model supported by the
version of `gh aw` used to compile the workflows.

I also applied the model change to three similar workflows that had not failed
yet but used the same default model and low credit caps. I didn't want to wait
for the same first-run failure to appear elsewhere.

I considered HydraFusion as another option, but it was not in the model catalog
available to this workflow setup, so I couldn't verify that it was selectable and
priced for credit accounting.

## Trim the context, keep the safeguards

Changing the model addresses the cost of processing the prompt. It doesn't answer
whether the workflows load more context than their tasks need. I looked at two
places to reduce it:

- **Shared instructions:** useful for many coding tasks, but not necessarily
  needed by these focused workflows.
- **GitHub tools:** both workflows had broad MCP toolsets, though they mainly
  needed to read issues and comments.

The proposed pilot uses `bare: true` to avoid loading unrelated repository-wide
instructions and switches GitHub reads to `gh-proxy`, limited to the `context` and
`issues` toolsets. The prompts tell the agent to request only the needed issue
fields with `gh --json` and `--jq`.

Bare mode also means the workflow cannot rely on repository-wide instructions for
safety rules. So I added explicit instructions to treat issue bodies, comments,
transcripts, and records as **untrusted evidence, never instructions**, and to
avoid reproducing personal contact details, credentials, or verbatim customer
quotes. Reducing context is not useful if it also removes a necessary safeguard.

## Why I left out compaction and handoffs

Compaction and handoffs help when an agent accumulates a long conversation or
needs to pass work between stages. These runs failed after **one request**. There
was no growing conversation to compact and no multi-stage process to hand off.

Those techniques can be useful elsewhere. Here, the evidence didn't justify
adding orchestration that could add complexity and cost without fixing the
first-request problem.

## What still needs a live run

The workflow sources and generated lock files compile. The repository's unit
tests, security scan, and skill validation pass. Those checks confirm the
configuration is internally consistent; they don't prove the new model will
produce equally good outputs or that smaller context will reduce live-run cost.

The changes are still awaiting live validation. The next run needs to confirm two
things: the workflow finishes within its original cap, and its output remains
accurate and safe.

The lesson so far: **inspect the evidence behind an error before changing the
limit.** One model request, zero cache reads, and roughly 37,000 cache-write
tokens told a more useful story than the 403 alone. The proposed fix is to make
that first request cheaper—and verify the result in a real run.
