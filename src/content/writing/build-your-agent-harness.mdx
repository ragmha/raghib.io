An agent needs more than a model call. The model proposes a next step; the
runtime validates it, checks policy, executes it, records what happened and
decides when to stop. That runtime is the **harness**.

Building a small one by hand makes those boundaries easier to see. Framework
docs then become a set of choices you can evaluate for your system, rather
than a black box to accept wholesale.

In this tutorial, you will build a harness in TypeScript with
[Bun](https://bun.sh). It uses a deterministic scripted model, so there is no
API key, network call or randomness. The behavior is repeatable and testable.
By the end, you will have:

- a provider-neutral model contract and a scripted model;
- a typed tool registry that validates tool names and arguments;
- a bounded, cancellable agent loop with a trace;
- skill loading, context projection and an evaluation report;
- an event-sourced runtime with in-memory replay;
- policy gates, approval checkpoints and an example idempotency boundary.

The central idea: **agent systems are workflow systems.** The model proposes a semantic next step. The harness owns state, execution, policy, limits and traces; errors propagate to the caller.

```mermaid
flowchart LR
    accTitle: How the harness turns a proposed step into recorded events
    accDescr: Context built from a skill, facts and history goes to the model, which proposes the next step. A tool call passes a policy gate: allowed calls run typed, schema-validated tools, and denied calls or calls awaiting approval are recorded directly. Final answers and tool results are also recorded as events with state and checkpoints, and resuming feeds those events back into the context.
    context["Context<br/>skill + facts + history"] --> model["Model<br/>proposes next step"]
    model -- "tool call" --> gate{"Policy gate"}
    model -- "final answer" --> events
    gate -- "allow" --> tools["Typed tools<br/>schema validated"]
    gate -- "deny or await approval" --> events
    tools --> events["Recorded events<br/>state + checkpoints"]
    events -- "resume" --> context
```

This walkthrough follows the [build-your-harness](https://github.com/ragmha/build-your-harness) exercise, and its [finished code](https://github.com/ragmha/build-your-harness/tree/e2b8166485b58d6ef711002e9128acf213138716) is on the `solution` branch. The core harness steps are covered by its 38 tests. The final coding-agent section is an extension beyond the exercise; its file tools are shown separately and are not included in that test count. Each step below shows the lines that carry the idea and links to the full file in the finished code.

## Prerequisites

Before you begin, ensure you have the following installed:

- [Bun](https://bun.sh/docs/installation) 1.3.14 or later. It runs TypeScript directly, installs packages and runs tests, so you do not need Node.js.
- Git, plus a browser and account on the host where you will create your template copy.
- Basic TypeScript.

## Step 1: Define the model boundary

Start with the smallest possible contract: messages go in, a response comes out. Nothing here names a vendor, so a real API, a local model and the scripted model all fit behind the same interface.

```ts title="src/core/contracts.ts"
export interface ToolCall {
  id: string;
  name: string;
  arguments: unknown;
}

export interface ModelAdapter {
  complete(request: ModelRequest, signal: AbortSignal): Promise<ModelResponse>;
}
```

Notice `arguments: unknown`. Whatever a model sends is untrusted input until the harness proves otherwise. The [full contract](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/core/contracts.ts) also defines messages, requests, responses, tool definitions and the trace events used in Step 2.

Failures get a typed [error](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/core/errors.ts), so callers can branch on `error.code`, such as `UNKNOWN_TOOL` or `MAX_STEPS`, instead of parsing messages.

Now the model itself. [`ScriptedModel`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/providers/scripted-model.ts) returns one canned response per call:

```ts title="src/providers/scripted-model.ts"
// … throw ABORTED first if the signal has fired
const response = this.#responses[this.#cursor];
if (!response) {
  throw new HarnessError("MODEL_EXHAUSTED", "Scripted model has no responses left");
}
this.#cursor += 1;
return structuredClone(response);
```

Three small decisions carry a lot of weight:

1. **Check cancellation first**, before consuming a response.
2. **Fail with a typed `HarnessError`**, not a plain `Error`.
3. **Return a clone**, so no caller can mutate the script and change a later answer.


## Step 2: Build a safe tool-calling loop

The model may propose a tool name and arguments. Your code decides which tools exist, validates the input, bounds the loop and records what happened.

### A tool is a schema plus a function

The template's [`lookup_code`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/tools/lookup-code.ts) tool reads a small synthetic, read-only table, and declares its input like this:

```ts title="src/tools/lookup-code.ts"
schema: z.object({
  code: z.string().trim().min(1).transform((value) => value.toUpperCase()),
}),
```

The schema does double duty. It is converted to JSON Schema to tell the model what the tool accepts, and it parses tool arguments before a tool runs. One source of truth reduces manual drift for constraints representable in JSON Schema; runtime parsing remains authoritative for transforms and refinements. The `transform` also normalizes input, so `alpha` and `ALPHA` find the same entry.

### The registry is the allowlist

[`ToolRegistry`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/tools/registry.ts) keeps registered tools by name. Its `execute` method checks the name, then the arguments:

```ts title="src/tools/registry.ts"
const tool = this.#tools.get(name);
if (!tool) {
  throw new HarnessError("UNKNOWN_TOOL", `Unknown tool: ${name}`);
}
const parsed = tool.schema.safeParse(input);
if (!parsed.success) {
  // … join the Zod issues into one readable message
  throw new HarnessError("INVALID_ARGUMENTS", `Invalid arguments for ${name}: ${issues}`);
}
return await tool.execute(parsed.data, context);
```

A hallucinated tool name fails as `UNKNOWN_TOOL`. Malformed arguments fail as `INVALID_ARGUMENTS`, with a message specific enough to feed back to a model. Code only runs after both checks pass. A tool can also declare an `effect`, which defaults to `read`; it matters in Step 5.

### The loop

This is the heart of the harness. [`runAgent`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/core/agent.ts) bounds the number of steps, combines caller cancellation with a timeout, calls the model, runs the requested tools one at a time and emits a trace event for each transition. Here is its loop:

```ts title="src/core/agent.ts"
while (true) {
  // … throw ABORTED if the caller cancelled or the timeout fired
  if (step >= maxSteps) {
    throw new HarnessError("MAX_STEPS", `Agent exceeded ${maxSteps} model steps`);
  }
  // … request the next step from the model and append its reply
  if (toolCalls.length === 0) {
    emit({ type: "run.finished", at: now(), step });
    return { output: response.content, messages, trace, steps: step };
  }
  // … run each requested tool in turn and append its result as a tool message
}
```

A few things to notice:

- **The run ends when the model stops asking for tools.** No tool calls means the content is the final answer.
- **`maxSteps` is checked before each model request**, so a confused model cannot loop forever and quietly spend your budget.
- **`AbortSignal.any`** merges the caller's signal and the deadline. The adapter and tools receive the signal, but cancellation is cooperative: each implementation must honor it, and filesystem calls in the example do not.
- **Model and tool calls share one `try`**, so every failure emits `run.failed` and is normalized to `ABORTED` when cancellation caused it.
- **The trace is not the context.** Trace events describe execution for you. They are never sent to the model.
- **`options.context`** is used in Step 3. Without it, the model sees the full history.


## Step 3: Skills, context and evaluations

A working loop is not yet a useful agent. It needs repeatable instructions, deliberate context and evidence that it behaves.

### Load a skill

A skill is a `SKILL.md` with optional `references/*.md`. The template includes one: its [`SKILL.md`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/fixtures/sample-skill/SKILL.md) tells the model to use `lookup_code`, return the tool's value exactly, say `Code not found.` when the lookup returns no value and never invent entries, and [`references/codes.md`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/fixtures/sample-skill/references/codes.md) lists the two synthetic codes.

The [loader](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/skills/load-skill.ts) reads the instructions, finds the references with `Bun.Glob`, and sorts them so the same skill always renders the same prompt.

### Project context instead of sending everything

Keep three ideas apart:

- **State** is what the runtime knows now: the cursor, the step count.
- **History** is what happened: every message and trace event.
- **Context** is what you choose to send the model this turn.

[`projectContext`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/context/project-context.ts) puts the instructions first, adds known facts as one sorted system message, then keeps the newest history that fits a message budget:

```ts title="src/context/project-context.ts"
// Walk blocks from newest to oldest. The block that crosses the target is
// kept whole, so a tool result never arrives without its tool call.
// …
for (let index = blocks.length - 1; index >= 0 && included < target; index -= 1) {
  const block = blocks[index]!;
  selected.unshift(block);
  included += block.length;
}
```

One rule makes it correct: an assistant tool call and its tool results form an indivisible block. The projection may exceed the budget rather than send a tool result whose call was cut off, which most providers reject. The budget is a message count, not a tokenizer, to keep the idea visible.

### Evaluate behavior

[`evals/evals.json`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/evals/evals.json) pairs a prompt with a scripted model and an expected answer. Its `lookup-alpha` case asks `What does ALPHA mean?`, scripts a `lookup_code` call and then the answer, and expects `Alpha is the first synthetic entry.`

The [report](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/evals/types.ts) has a fixed shape: a timestamp, totals for cases, passes and failures, and one result per case with its expected and actual output and step count.

The [runner](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/evals/run-evals.ts) validates the file with Zod, gives each case a fresh model and registry (a `ScriptedModel` has a cursor, so sharing one would leak state between cases) and compares outputs.

A small [CLI](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/evals/cli.ts) writes the report and fails the process when a case fails, so CI can block a change that makes the agent worse.

## Step 4: Make execution event-sourced

An in-memory call stack disappears when a process stops. An event-sourced runtime records facts and rebuilds current state by replaying them. This tutorial's store is in memory: it demonstrates replay after rebuilding a harness instance in the same process, not recovery after a process crash. Real crash recovery requires a persistent store with suitable transaction and durability guarantees.

### Events, state and checkpoints

The template defines the event and store contracts in [`src/durable/contracts.ts`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/contracts.ts). Read them before writing the reducer:

```ts title="src/durable/contracts.ts"
export type RunEvent =
  | { type: "model.responded"; response: ModelResponse }
  | { type: "approval.requested"; request: ApprovalRequest }
  | { type: "approval.resolved"; resolution: ApprovalResolution }
  | { type: "tool.denied"; toolCall: ToolCall; reason: string }
  | { type: "run.completed"; output: string }
  // … plus run.started, policy.decided, tool.completed and run.failed
```

Four objects, four jobs:

1. `RunEvent` records what happened. The event list is the source of truth.
2. `RunState` is the current control position.
3. `RunSnapshot` is state plus message history.
4. `RunCheckpoint` caches a snapshot up to one version. It is only an optimization.

### The reducer

State is a pure function of events. Nothing in [the reducer](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/reducer.ts) performs I/O:

```ts title="src/durable/reducer.ts"
const start = checkpoint ? structuredClone(checkpoint.snapshot) : initialSnapshot(runId);
const throughVersion = checkpoint?.throughVersion ?? 0;
return events
  .filter((entry) => entry.version > throughVersion)
  .reduce((snapshot, entry) => applyRunEvent(snapshot, entry.event), start);
```

Two details matter. `replayEvents` starts from a checkpoint but still applies every event after `throughVersion`. And a repeated tool call ID throws `DUPLICATE_TOOL_CALL`, so a misbehaving model cannot make the harness run the same call twice.

### The store

[`InMemoryRunStore`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/in-memory-store.ts) uses optimistic concurrency. Every commit says which version it expects; a stale writer gets `VERSION_CONFLICT` instead of silently overwriting another worker's progress:

```ts title="src/durable/in-memory-store.ts"
const current = this.#runs.get(request.runId) ?? { version: 0, events: [] };
if (request.expectedVersion !== current.version) {
  throw versionConflict(request.runId, request.expectedVersion, current.version);
}
```

It survives reconstructing the harness inside one process because the same `Map` remains alive. It does not survive a process exit. A database adapter would also need atomic commits and durability guarantees; implementing the same interface alone would not provide them.

## Step 5: Add policy gates and an idempotency example

Event replay does not decide whether a proposed tool is allowed, or close the gap between performing an effect and recording that it happened.

### Policy is data

Before any tool runs, a `PolicyGate` returns `allow`, `deny` or `require_approval`. [`StaticToolPolicy`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/policy.ts) looks the decision up by tool name:

```ts title="src/durable/policy.ts"
evaluate(input: PolicyInput): PolicyDecision {
  const decision = Object.hasOwn(this.decisions, input.call.name)
    ? this.decisions[input.call.name]
    : undefined;
  return structuredClone(decision ?? this.fallback);
}
```

The fallback is `deny`: a tool nobody configured does not run. `Object.hasOwn` matters too, so a tool named `constructor` cannot inherit a decision from `Object.prototype`. The harness persists the decision before acting, so a policy change mid-run cannot silently alter a call that was already judged.

### Close the effect-before-commit window

A write tool can succeed, then the process can die before `tool.completed` is recorded. On retry, the tool may run again. A key alone does not prevent that: safe retries require the destination to persist and atomically honor the key with the effect. This [in-memory example](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/effect-sink.ts) only deduplicates while its `Map` survives; the demo tools do not use it:

```ts title="src/durable/effect-sink.ts"
recordOnce(key: string, value: T): { created: boolean; value: T } {
  if (!this.#records.has(key)) {
    this.#records.set(key, structuredClone(value));
    return { created: true, value: structuredClone(value) };
  }
  return { created: false, value: structuredClone(this.#records.get(key) as T) };
}
```

This only works if the real destination honors the key. Many external systems do not, which is a design question worth asking before you let an agent write to them.

## Step 6: Pause at an approval checkpoint

An approval checkpoint should be recorded rather than held in a pending `Promise`. This example records it in the in-memory store, so only another harness instance in the same process can resolve it.

The end-to-end teaching harness is [`DurableHarness`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/durable/harness.ts). Each loop iteration of its `drive` method rereads the store, replays the run and takes one next action:

```ts title="src/durable/harness.ts"
while (true) {
  const stored = requireStoredRun(runId, await this.store.read(runId));
  const snapshot = replayStoredRun(stored);
  // … return if the run completed, failed or waits for approval
  if (call) {
    await this.processToolCall(stored, snapshot, call);
  } else if (state.steps > 0 && snapshot.history.at(-1)?.role === "assistant") {
    // … no tools were requested: record run.completed with the final answer
  } else if (state.steps >= state.maxSteps) {
    // … record run.failed with MAX_STEPS
  } else {
    // … call the model, then record model.responded
  }
}
```

Walk through `drive` once and the example's control flow becomes clear:

- **One event, then reread.** Each pass records an event, then the loop rereads the in-memory store. The recorded event can be replayed while that store remains available; a process exit loses it.
- **Model responses are recorded before tools run.** Within this process, a committed response is not requested again during replay. This is not a guarantee across a process crash or a failed store write.
- **Policy before effects.** A pending tool call gets a recorded decision, then is denied, paused, or executed. Own-property checks and safe record writes prevent inherited object properties from being mistaken for decisions; add regression cases for `constructor`, `toString` and `__proto__` IDs.
- **Approval is bound to a recorded call, not an authenticated person or an exact diff.** The command cannot change the call, but this sample does not authenticate approvers or bind approval to a resolved path, content hash or preview.
- **The `fault` hook** injects exceptions at three points. It does not simulate killing the process or prove storage durability.

## Turn the harness into a coding agent

The same loop can power a small coding agent: the model reads a file, lists a directory, proposes a change, then explains what it did. This is the core idea behind [“How to code Claude Code in ~200 lines of code”](https://youtu.be/s7ZzkdvCMDY): the first useful coding agent is a model loop connected to a few tools, not a giant framework.

Keep its reach narrow. Give it one workspace directory, no shell tool, and three file tools. Reading and listing are non-mutating but can expose secrets or send sensitive workspace content to a remote model; apply an explicit read policy and size/type limits. Route edits through an approval policy.

### Add example file tools with a workspace path check

These [tools](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/tools/filesystem.ts) use Node's file and path APIs, which Bun implements. The path check rejects ordinary `../` escapes and existing symlinks that resolve outside the workspace. It is not a security sandbox: validation and file access are separate operations, so concurrent changes can create a time-of-check/time-of-use race; hard links are not detected. Treat the workspace as trusted and not concurrently modified, or use OS-level confinement for untrusted workspaces. `list_files` shows only the immediate directory and skips symlinks; it does not recursively walk the workspace.

```ts title="src/tools/filesystem.ts"
if (isAbsolute(requested)) throw new Error("Use a workspace-relative path");
const workspace = await realpath(root);
const path = await realpath(resolve(workspace, requested || "."));
const fromRoot = relative(workspace, path);
if (fromRoot === ".." || fromRoot.startsWith(`..${sep}`) || isAbsolute(fromRoot)) {
  throw new Error("Path is outside the workspace");
}
```

Register the tools and make policy explicit in [`src/coding-agent.ts`](https://github.com/ragmha/build-your-harness/blob/e2b8166485b58d6ef711002e9128acf213138716/src/coding-agent.ts). The sample records a policy decision before acting, but the approval is requested for raw model arguments: path resolution, exact-match selection and diff generation happen later. It does not show or bind approval to the exact change. Do not use it to authorize real writes without resolving the target and previewing and binding the exact diff first.

```ts title="src/coding-agent.ts"
const policy = new StaticToolPolicy({
  list_files: { kind: "allow" },
  read_file: { kind: "allow" },
  edit_file: { kind: "require_approval", reason: "Review the proposed file change" },
});
```

With `workspace/notes.txt` containing `TODO`, as in the finished code, the demo reads the file, then pauses before editing. It prints the requested arguments, not a resolved target or diff:

```bash
bun run src/coding-agent.ts
```

```text
waiting_for_approval
{"path":"notes.txt","oldText":"TODO","newText":"Done"}
```

The file-tool example is illustrative and has no tests in the linked template. Before using it, add checks for path traversal, symlink races, stale files, exact diff approval, sensitive reads and file-size limits. Exact-match replacement only fails when the old text is missing or ambiguous; it does not prevent a target from changing after approval.

### Swap in a real model

`ScriptedModel` implements `ModelAdapter`. A basic non-streaming provider adapter can send `request.messages` and `request.tools` and map a compatible response into `ModelResponse`. TypeScript interfaces do not validate provider payloads at runtime, so validate the full response and tool-call IDs at this boundary. Providers differ in schema support, tool results, parallel calls, retries and cancellation, so the adapter may require orchestration changes too. This tutorial tests only the scripted adapter.

Start with the scripted model. The file tools and approval flow need their own tests before they are used with real files.

This is a small coding agent, not a production clone of Claude Code. It has no shell access, recursive search, patch application, terminal session, or multi-file plan. Add a capability only when a real task needs it; keep each new write behind approval.

## Summary

You now have a small teaching harness in about a dozen files with two dependencies. It:

- demonstrates an adapter interface with a scripted model;
- only runs allowlisted tools, with validated arguments;
- caps model steps and propagates cooperative cancellation when providers and tools honor the signal;
- traces every step without leaking that trace into the prompt;
- projects context and runs example evaluations;
- replays events only while its in-memory store remains available;
- exposes an approval-command API without approver authentication or exact-diff binding;
- includes file-tool examples with a path check, not OS-level workspace confinement.

None of this depends on a particular model, cloud or industry. Whether your agent triages support tickets, reconciles invoices or files maintenance orders, the questions are the same: which actions exist, who may approve them, what happens on retry, and how you will know it still works tomorrow.

## Where to go next

- **Use a real model.** Write and test a `ModelAdapter` for a specific provider's contracts, including its tool-call format, schema limits, retries and cancellation.
- **Use a real store.** Implement `RunStore` on a database with atomic commits and a unique `(runId, version)` constraint; test process-kill recovery and define durability guarantees.
- **Expose tools over MCP.** The [Model Context Protocol tools specification](https://modelcontextprotocol.io/specification/latest/server/tools) standardizes discovery and invocation between processes. The registry here is the in-process version of the same idea.

What this deliberately leaves out is just as instructive: plugin loading, dependency injection, streaming and multi-agent orchestration. Add them when a real requirement asks for them, and you will know exactly which seam they plug into.
